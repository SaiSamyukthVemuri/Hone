# hone-release: install steps for Sam (root on the VPS; nothing here was run on it)

Prerequisite and headline limit (now ENFORCED): `install.sh` REFUSES, with no override, when the agent user is a member of `docker`, `sudo`, `wheel`, `lxd` or `adm`. **this custody holds only if the agent user is in neither the `docker` nor the `sudo` group.** On this VPS `sam` is in both (`groups=sam,sudo,users,docker`). Docker-group membership is root-equivalent (`docker run -v /var/lib/hone-release/secrets:/s ... cat` reads the secrets; CI shows it), and sudo-group membership means `sudo -l` shows a general ALL rule and a sudo password typed in an agent's pane gives that pane root. Moving the lanes' docker use to another user (or rootless docker) and removing the agent user from both groups is **your decision** and blocks the custody claim until done.

1. **Pins first.** From the REVIEWED record (the END and PR of this package, not from the package itself) type the sha256 of every package file into a pins file that only root can write and that lives OUTSIDE the package: `sudo install -m 644 -o root -g root /dev/null /root/hone-release-pins.txt`, then paste lines `<64 hex>  <relative path>` for every file (launcher, install.sh, set-secret.sh, approve-package.sh, bind-gonogo.sh, actions.conf, sudoers.hone-release, ca/supabase-prod-ca-2021.crt, scripts/*.sh, scripts/mgmt-read.py, scripts/wal-evidence.py, scripts/pitr-wal-status.sql (sha256 must be c91d7a497ce3b04b88aedd72c8b2729694b65c3c5cc2f051837e3f2365ad8cd5, the Insurance-approved file), bind-serving.sh, tools/make-verify-bundle.py (including verify.sh and post-s3-smoke.sh, whose sha256 must be 0c69ce828a982234d97751284514bdd9d7d3af026871e572bfd799bfe614571c, the OPS-reviewed smoke), DELTAS.md, INSTALL.md, ci/*). There is NO SHA256SUMS file inside the package (it would be an unpinned file, and the installer refuses any file the pins do not list); the shas to type are in the reviewed END, and `hon66-release.SHA256SUMS.txt` next to the package directory in the handoff folder is only a convenience for comparing.
2. Copy `hone-release/` and the linux supabase-go (verified: archive `9c0421ba…`, inner `174a90e2…`) into a **root-owned directory with no world-writable ancestor** (for example `/root/hone-release-pkg`, not /tmp), run `sha256sum install.sh` and compare it with the reviewed record, then: `sudo bash install.sh <agent-user> <project-ref> <path-to-supabase-go> /root/hone-release-pins.txt`. It refuses unless every file matches its pin and the package holds exactly the pinned files. It creates the `hone-release` system user, the directories (700), the root-owned launcher, scripts and manifest (built from the pins), the sudoers line (checked by `visudo -cf` first). It writes no secret and no approval.
3. `sudo bash set-secret.sh db-password` and `sudo bash set-secret.sh read-pat` — each at a hidden prompt, typed twice. Two files, two actions: the apply action receives ONLY the database password (the CLI needs no token for `--db-url`); read actions receive ONLY the read-only PAT (Database Read + Backups Read). Record the rotation dates.
4. Per stage (with the person present and the window open): the agent copies `bundle.tar` and `list.sha256` into `/srv/hone-release-inbox` (mode 644); you run `sudo bash approve-package.sh id=... bundle_sha=<64 hex from the reviewed record> list_sha=<64 hex> head=<40 hex> pr=<number> receipt_sha=<64 hex> first=0213 last=0246 count=34 minutes=<=60 window_start=<UTC> window_end=<UTC> recovery_basis=row4|waiver waiver_id=WAIVER-YYYYMMDD-N|none (typed from the recorded waiver; any other form is refused) recovery_stamp=<UTC>|none s0a_sha=<64 hex> s0a_at=<UTC> min_span_days=6 quiet_db=idle|heartbeat connection_mode=direct|pooler pooler_host=<aws-N-region.pooler.supabase.com:5432>|none history_before=<rows> s0a_writes=<digits>|none drain_holds=yes drain_queues=yes drain_people=yes drain_max_busy=<0..99> drain_attestation="<words>" serving_commit=<40 hex> serving_attestation="<words>" verify_sha=<64 hex>|none statement_timeout_s=<1..600> lock_timeout_s=<1..30> idle_tx_timeout_s=<1..300> max_push_seconds=<10..1800> attestation="<your words>"`. The values are typed from the reviewed record, never from the script's output; it recomputes them from the inbox and refuses on any difference. Sam's per-stage approval is that command. The record is single-use and is consumed at the first dry-run attempt.
5. The agent runs `sudo -n -u hone-release /usr/local/libexec/hone-release/launcher apply` (or `read-backups`, `wal-capture`, `idle-probe`, `heartbeat`, `reconcile`, `preflight`, `verify`, `status`, `read-s1read`, `read-gap`) — the only eleven commands the sudoers line allows. Autonomous order for one stage: `read-backups` (and `idle-probe`, or `heartbeat` then `read-backups` again after the recovery point advances), then `preflight` (print the GO/NO-GO package; the approver reads it and runs `sudo bash bind-gonogo.sh gonogo_sha=<64 hex>`), then `apply`, then `verify`. See RELEASE-QUEUE.md.
6. Anything but a clean APPLIED state blocks the next run; only root clears `/var/lib/hone-release/state/APPLY-STATE` after the migration history has been read back.

## Dependencies on the host

`bash`, `python3` (3.8 or newer, run as `python3 -I`), `openssl`, `sha256sum`, `tar`, `sudo` and, for `read-s1read` and `read-gap` only, a SYSTEM **Node 18 or newer at `/usr/bin/node`** (the launcher's PATH is `/usr/bin:/bin`, so a Node in a home directory or `/usr/local/bin` is not found and those two actions stop with "node not found"). Use a patched release (22.23.4 or 24.22.1). Install it before relying on those actions; the other actions do not need Node.
